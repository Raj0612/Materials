CSRF:
*****
By default CSRF will be applied to POST, DELETE, PUT which are used to alter the data.

CSRF Token : Used to prevent CSRF attack. It will be unique per user session. It is also called as XSRF token. CSRF Token should be sent by the UI to the backend in each request  either in header or payload along with CSRF cookie by the browser.

CsrfToken interface is used to create the CSRF Token by Spring. Use CookieCsrfTokenReposity class as storing CSRF Token in cookie is better than stoting is session.

To create custom CSRFCookieFilter:
---------------------------------- 
Create a class CSRFCookieFilter by extending OncePerRequestFilter and override doFilterInternal method.

Add this is SecurityConfig class
	http.csrf(csrfConfig -> csrfConfig.csrfTokenRepository(CookieCsrfTokenReposity.withHttpOnlyFalse()))
		.addFilterAfter(new CSRFCookieFilter(), BasicAuthenticationFilter.class)

Note:
-----
withHttpOnlyFalse :- js code also will read the cookie.

To read CSRF token on each Request:
------------------------------------
1) Create object of CsrfTokenRequestAttributeHandler in SecurityConfig class.
2) Add  .csrf(csrfConfig -> csrfConfig.csrfTokenRequestHandler(CsrfTokenRequestAttributeHandlerObj)) in SecurityFilterChain.

CsrfFilter is responsible for validating the CsrfToken

JWT TOKEN:
*********

JWT Token has 3 parts : header, payload and signature
header has information like what algorithm used and like that
payload : has info about user, created , expiration details
signature is crerated by using formula HMACSHA256(baseUrlEncode(header) + "." + baseUrlEncode(payload), secret)

Steps to create JWT TOken:
--------------------------
1) Create Filter for generating JWTToken by extending OncePerRequestFilter.
2) Override doFilterInternal and implement logic for creating JWT Token.
3) Override shouldNotFilter method with code (return !request.getServletPath().equals("/user");)
4) Create Filter for validating JWT Token by extending OncePerRequestFilter.
5) Override doFilterInternal and implement logic for validating JWT Token.
6) Override shouldNotFilter method with code (return request.getServletPath().equals("/user");)
2) Add addFilterAfter(JWTCreateFilterObj, BasicAuthenticationFilter.class) :- For creating JWT token after login success
3) Add addFilterBefore(JWTValidateFilterObj, BasicAuthenticationFilter.class) :- For validating JWT token after login success

OAUTH2: Open Authorization
===========================

OAuth2 has grant types as below
*) Authorization Code
*) PKCE
*) Client Credentials
*) Device Code
*) Refresh Token
*) Implicit Flow(Legacy)
*) Password Grand(Legacy) 

1)AuthorizationCode - Flow will be by 2 types 
	*) To get the authorizaton code(clientId, response_type="code", scope(READ, WRITE etc), state(CSRF token to protect from CSRF attacks), redirect_uri) . Authe server will send code and the state with value which we send earlier
	*) Then to get access token(clientId , clientSecret , authcode, grant_type="authorization_code", redirect_uri). In both redirect_uri needs to be send.
	
2)Implict Grand Flow - (client_id,redirect_uri,scope,state, reponse_type="token"). ClientSecret is not involved since it is a get request. Here only one request to auth server to get the access token. It's not secure as the token value will be redirected in the url. In response we will get the access_token along with the state with value which we send earlier

3)Proof Key For Code Exchange(PKCE) -- Used for public clients(native and SPA) as public clients cannot securely store a Client Secret. Using code_verifier only the code_challenge(has value of code_verifier) is created by using the code_challenge_method.
	*) To get Authorization code (clientId, redirect_uri, scope, state, reponse_type="code", code_challenge, code_challenge_method=SH256). Authorization Server stores the code_challenge and sends the authorization code.
	*) To get access token(clientId , clientSecret , code, grant_type="authorization_code", code_verifier)code_challenge is the has representation of code_verifier. Auth Server verifies the code_challenge by the code_verifier which is send now and if valid it will send the access token. clientId & clientSecret are optional.
	
4)Password Grant Type -- Here user credentials(username & password) is shared. Used if Auth Server, Resource server and client belongs to same origanization as user credentials are shared. This grant type is deprecated.
	*) To get access token (client_id, client_secret, scope, grant_type="password" username="" , password="")
	
5) Client Credentials Grant Type :- Used when no end user involved, means when 2 backend application tries to communicate.
	*)  To get access toke (client_id, client_secret, scope, grant_type="client_credentials"). We can use this flow if there are no user and ui involved.
	
6) Refreh Token Grant Flow: 
	*) When using AuthorizationCode & PKCE grant flow we will get access token and refresh token.
	*) When accessToken is expired refresh Token grant flow will be initiated using refresh token.
	*) client_id, client_secret, refresh_token, scope, grant_type ="refresh_token"
	*) offline_access scope is used to get a refresh token that never expires.
